# Developer Guide

Welcome to the arXiv Insight developer guide. This document explains the system architecture in depth, the development workflow, and how to modify each layer of the stack.

## 🏗 Architecture Overview

The system is composed of four services orchestrated by Docker Compose:

1. **Data Ingestion (`agy-ingest` CLI)**: A Typer-based CLI tool that fetches papers from the arXiv Atom API, parses the XML response (using an XXE-safe `lxml` parser), normalizes metadata (author names, abstracts, timestamps), generates 384-dimensional dense vectors locally using `fastembed` (`BAAI/bge-small-en-v1.5` via ONNX Runtime), and upserts them into PostgreSQL. Includes tenacity-based retry logic, 3.1-second rate limiting, savepoint-level error isolation per paper, and in-run deduplication.
2. **PostgreSQL Database (`pgvector`)**: Stores relational metadata (papers, authors, categories via normalized join tables) and dense vector embeddings. The hybrid search engine uses **Reciprocal Rank Fusion (RRF)** to combine a GIN-indexed Full-Text Search vector (`tsvector`, generated by a Postgres trigger) with an HNSW-indexed Cosine Similarity vector search — all in a single SQL query.
3. **Redis**: Powers the `SlowAPI` tiered rate limiter (5/minute on RAG, 60/minute on stats) with graceful fallback to in-memory storage if Redis is unavailable. Also aggressively caches heavy statistical dashboard queries (5-minute TTL) with automatic cache invalidation after every successful ingestion run.
4. **FastAPI Backend (`app.main`)**: Serves the REST API, the Advanced RAG endpoint (powered exclusively by Groq), Prometheus metrics (`/metrics`), health probes (`/healthz`, `/readyz`), and the static HTML/CSS/JS frontend dashboard.

### Data Flow

```text
arXiv Atom API ──► agy-ingest CLI ──► Parser ──► Normalizer ──► PostgreSQL (pgvector)
                                                       │
                                                       ▼
                                              fastembed (local ONNX)
                                                       │
                                                       ▼
                                            paper_embeddings table (HNSW)

User Question ──► /api/v1/ask ──► Embed Query (local) ──► Hybrid RRF Search ──► LLM (Groq) ──► JSON Response
                                                                                    │
                                                                               (extractive fallback
                                                                                if no API key)
```

## 🛠 Development Workflow

### 1. Environment Setup
We use standard Python packaging via `pip` and `pyproject.toml`.
```bash
# 1. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate

# 2. Install the project in editable mode WITH developer dependencies
pip install -e ".[dev]"

# 3. Spin up the local database and redis
make up
```

### 2. Making Database Changes
If you need to change the database schema (e.g., adding a new column to `papers`):
1. Modify the SQLAlchemy model in `src/app/db/models/` (e.g., `paper.py`).
2. Make sure the model is imported in `src/app/db/models/__init__.py` so Alembic can discover it.
3. Generate a new Alembic migration:
   ```bash
   alembic revision --autogenerate -m "Add new column"
   ```
4. The `migrate` container will automatically apply this migration the next time you run `docker compose up --build`.

> **Note:** The `migrations/env.py` dynamically injects `settings.DATABASE_URL` at runtime, overriding the dummy default in `alembic.ini`. This ensures migrations work identically in Docker and local environments.

### 3. Adding a New API Endpoint
1. **Schema:** Define request/response Pydantic models in `src/app/api/schemas/`.
2. **Repository:** Add the data access method in the appropriate `src/app/db/repositories/` file.
3. **Service:** Add business logic in `src/app/services/`.
4. **Router:** Create or extend a router in `src/app/api/routers/`, and register it in `src/app/api/router.py`.
5. **Rate Limit:** Apply `@limiter.limit("60/minute")` decorator if needed.

### 4. Modifying the Frontend
The frontend is written in pure HTML/CSS/Vanilla JS and is located in `src/app/static/`.
- Because the `Dockerfile` and local environment install the project in "editable" mode (`pip install -e .`), any changes you make to the static files are instantly reflected upon browser refresh.
- The dashboard fetches data from `/api/v1/stats/visualization` and renders interactive charts. To add a new chart, extend the `VisualizationResponse` schema, add the query in `StatsRepository`, and update the frontend JS.

### 5. Changing the LLM Provider
The LLM integration is in `src/app/services/llm.py`. Currently, only Groq is supported via the `groq` SDK:
1. Set `LLM_PROVIDER=groq` and `LLM_API_KEY=<your-key>` in `.env`.
2. Set `LLM_MODEL=llama3-70b-8192` (or any Groq-supported model).
3. If `LLM_PROVIDER=none` (default), the system falls back to a local extractive mode that surfaces the top-3 abstracts without calling any external API.

To add a new provider (e.g., OpenAI), add a new enum value to `LLMProvider` in `settings.py`, then add a new branch in `LlmService.generate_rag_answer()`.

### 6. Running the Pipeline Locally
To test the full RAG pipeline locally:
```bash
# 1. Ingest papers
make ingest

# 2. Start the API locally (or use Docker)
uvicorn app.main:app --reload

# 3. Test the RAG Evaluation metrics
make eval
```

### 7. Running Tests
Tests use **Testcontainers** to spin up a real PostgreSQL + pgvector container, then run Alembic migrations inside it. No mocking of the database layer.
```bash
make test
```

> **Important:** Redis and Docker must be running for integration tests that touch rate limiting or stats caching. Unit tests (parser, normalizer) run without any external dependencies.

## 📐 Key Design Patterns

| Pattern | Where | Why |
|---|---|---|
| **Repository Pattern** | `src/app/db/repositories/` | Isolates raw SQL/ORM from business logic. Services never touch SQLAlchemy directly. |
| **Protocol-based DI** | `EmbedderProtocol`, `LlmProtocol` | Enables swapping fastembed/Groq with mocks in tests without monkey-patching. |
| **Content Hash Gating** | `papers.content_hash` vs `paper_embeddings.content_hash` | Only re-embeds papers whose text actually changed, saving compute on incremental ingests. |
| **Savepoint Isolation** | `session.begin_nested()` in ingestion | A single paper failure doesn't roll back the entire batch — the run continues. |
| **Graceful Degradation** | `limiter.py`, `stats.py`, `llm.py` | Redis down? In-memory rate limiter. No API key? Extractive fallback. LLM error? Safe abstention. |
